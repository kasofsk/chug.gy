Engineering, run as a fleet.

chuggy is the coordination layer for organizations that build software with AI agents. It holds all of an organization's work in a single graph, lets people and agents carry it forward together, and records every decision made along the way. How work is checked, reviewed and landed is yours to compose.

Why chuggy

The constraint on software has moved. Writing it is cheap now. Deciding what to write, keeping a hundred efforts coherent, and standing behind the result is not.

One engineer with an agent is already a small team. An organization of them is a fleet, and a fleet without coordination is not faster, only louder. Agents that cannot see each other's work pull in different directions. Tasks wait on tasks nobody wrote down. Something ships, and nobody can say exactly why.

Each earlier shift in how software is made produced a layer the organization could no longer do without. Version control. Continuous integration. The shift to agents needs one too. chuggy is that layer: the structured graph of all the work, the rules for how work moves through it, and the record of what happened.

How it works

One graph of the work

Every task is a ticket that says what it waits on. The organization sees the whole; each engineer tends their part. Nothing starts before what it depends on has landed, and nothing is lost in between.

A lead on every project

An agent that holds the whole picture rather than one task. It proposes what runs next, holds work that would conflict with work in flight, answers the team's questions, and writes down the reason for every decision.

Verification before trust

A worker's word is not evidence. The checks you write run, an independent reviewer judges the change, and a person approves where you require it. Every attempt keeps its transcript, its cost and its verdict.

Your fleet, your keys

Work runs on machines you control, from a laptop to a shared pool to the cloud, under your own model accounts. Code and credentials never leave your hands. A project grows by adding machines.

The path every change takes

  1. DraftWritten in chat, or by hand
  2. ReleasedReady for a machine to take
  3. WorkAn agent or a script does it
  4. ChecksYour tests, then an independent review
  5. ApprovalA person says yes, where you require it
  6. LandedA commit or a pull request in your repository

The same path for a one-line fix and a month of work, for a ticket a person wrote and one an agent did.

Built on itself

chuggy's own development runs on chuggy. Each change to it is a ticket that moved through the graph, passed its checks, and was approved by one of us before it landed. A game studio ships on it.

The core is a formal model, and the implementation is held to the traces that model produces. The orchestrator is public on GitHub, and the runners for Linux, macOS and Windows are open source. The docs describe how a project is set up and how its jobs run.
