Run your AI coding agents as one fleet.

Twenty developers with twenty agents cannot see each other's work, and the agents never talk. chuggy holds every ticket in one graph, runs the work across the machines you give it, and keeps the whole project coherent while each developer tends their own.

Today's coding agents are good. Give one a list and it will work through it. The trouble starts when a team does this, because every developer has their own list, their own agent and their own context, and nothing connects them. Two agents change the same thing in different directions. Work waits on work nobody wrote down. Someone asks what the agents did last week, and the answer is in forty transcripts on twenty laptops.

This gets worse with every person you add. The fix is a single workflow the whole organization's work moves through, with a view of all of it, while each developer keeps tending their own tickets.

One graph of all the work.

The graph

Every piece of work is a ticket, and tickets say what they wait on. A ticket does not start until what it depends on has landed, so a big ask splits into parts that run in parallel where they can and in order where they must. You can see the whole project at once, or just your own corner of it.

The lead

A project can have a lead, an agent that watches the whole graph rather than one ticket. It proposes what should run next, holds a ticket that would contradict work already in flight and writes down why, and answers questions from anyone on the team. Every decision it makes goes in a log you can read.

The people

Developers file tickets in chat or by hand and keep their own work moving. Reviewers approve what lands. Viewers watch. Each action is signed in and permission-checked, across workspaces and projects, so an organization can run many teams on one chuggy.

Every ticket moves the same way.

  1. DraftWritten in chat or by hand
  2. ReleasedReady for a machine to pick up
  3. WorkAn agent or a script does it
  4. ChecksYour commands, then a reviewing agent
  5. ApprovalA person says yes, where you require it
  6. LandedA commit or a pull request in your repository

A failed check sends the work back with the reason. Work that keeps failing parks and waits for a person. The agent that did the work does not judge it; a separate reviewing agent and the checks you wrote do. Each attempt keeps who asked, what model ran with what settings, the full transcript, every result, the cost, and the commit it became.

Work runs across your machines.

chuggy hosts the coordination. The work itself runs on runners you register, and a project can spread its tickets over as many of them as you have, on Linux, Macs and Windows. Your code and your AI credentials stay on hardware you control, and each machine uses its own Claude or Codex account.

Project pools
Machines a team shares. Any ticket in the project can run on any of them, and chat and the lead can run there too.
Personal runners
A developer's own machine, running only that developer's tickets in the projects they allow.
Kinds of work
A ticket names the environment it needs. Most run in a container of the project's image. Some run on the machine itself, for Unity, Xcode and tools like them.
Credentials
A Claude subscription or API key, Bedrock, Vertex AI or Foundry, or a Codex login, read by the job on the machine and scrubbed from what it reports.

What we have learned about long-running agents.

chuggy is opinionated. The opinions come from running agents unattended for a long time, on our own code and on a shipped game, and from watching where they go wrong.

  • Agents say they are done when they are not. So nothing lands on an agent's word. Checks you wrote run, a different agent reviews, and a person approves where it matters.
  • Long runs crash, and a crash must not land something twice. So one part of chuggy makes every decision and writes it down before acting. After a restart it reads the record and carries on.
  • Context is the scarce thing. So a lead that has spent its context hands off to a successor with a note, and a ticket carries what its worker needs rather than the whole history.
  • Nobody trusts what they cannot audit. So every attempt is on the record, and a reviewer can read exactly what ran, under which model, at what cost.
  • The rules have to be right before the code is. So chuggy's core is a formal model, and the implementation is checked against the traces that model produces.

Where it is.

Today

  • chuggy builds chuggy. Its own tickets run on it, and more than 750 pull requests have landed this way on the current version.
  • BattleBuffet, a game, is built on chuggy and streamed on Twitch.
  • The first outside team is running work on its own machines.

Next

For developers

Your repository names the environment

A project is one or more GitHub repositories. Each holds configurations in .chug/configurations/ that name the image a job runs in or the capabilities it needs, the work stage, the evaluation stages of check commands or reviewing agents, and how a ticket lands: a push, a pull request, or a pull request then a merge. Every key is in the published schema.

A job is a container of your image

It runs as uid 1000 with chuggy's runtime mounted read-only, the repository cloned to /workspace/repository, and 2 CPUs and 4 GiB unless the configuration asks for more. Build caches, Docker inside a job, and jobs on the machine itself are in the docs.

Two GitHub Apps split authority

Chuggy Portal lands finished work, and a repository rule can make it the only thing besides admins allowed to update main. Chuggy Worker is what a job's git credential is minted under, and the same rule refuses it on main.

Your own coding agent gets the same tools

On Linux, one line gives Claude Code the tools a chuggy session has, under your own sign-in.

claude mcp add chuggy -- chuggy-linux mcp --site https://chuggy.vteng.io --workspace … --project …

The lead is an agent with a mailbox

Each turn it sees the project's state, the tickets ready to run, and the refusals it has standing. It answers with what to dispatch, what to hold and why. A ticket leaves a hold by being authored again. Members can open an inquiry and ask it anything.
