What chuggy does

Describe the work.

Write what you need in chat, or file a ticket by hand. chuggy asks when something is unclear, splits a big ask into tickets that wait on each other, and a lead agent proposes what to start next.

Helpers do it. Other helpers check it.

Each ticket runs on a machine you registered, in the environment your project names. Checks you wrote and a reviewer that did not do the work judge the result. Work that keeps failing stops and comes to you.

You approve what lands.

A change lands in your repository as a commit or a pull request once a person says yes. Every attempt keeps who asked, what ran, what passed, what it cost, and what it became.

Every ticket follows the same line.

  1. DraftWritten in chat or by hand
  2. ReleasedReady for a runner to pick up
  3. WorkAn agent or a script does it
  4. ChecksYour commands, then a reviewer agent
  5. ApprovalA person says yes, where you require it
  6. LandedA commit or a pull request in your repository

A ticket waits for the tickets it depends on. A failed check sends the work back with the reason, and work that fails too often parks and waits for a person.

Why it exists

Coding agents are good at a task and hard to trust with a hundred of them. Left alone, they say they are done when they are not, repeat a step after a crash, and leave nobody able to say what happened. chuggy is the part of the system that keeps them honest.

  • Nothing reviews its own work

    A separate reviewer judges each change against your written standards, and the checks you wrote pass or fail it. The agent that did the work has no say in whether it lands.

  • A crash never lands something twice

    One part of chuggy makes every decision and writes it down before acting on it. After a restart it reads that record and carries on from where it was.

  • Work waits on work

    Tickets form a graph. Nothing starts before what it depends on is done, and the graph cannot loop.

  • Everything is on the record

    Each attempt keeps who asked, the model and its settings, the full transcript, every verdict, the cost, and the commit it became.

  • People steer while it runs

    Chat drafts and releases work. A lead agent proposes what starts next and waits for a yes. Anyone with the right role can stop a run or resume a parked one.

  • Many people, many projects

    Workspaces, projects, roles, read-only viewers and invite links. Every action is signed in and permission-checked.

Your machines. Your AI accounts.

chuggy hosts the coordination: the queue of tickets, the approvals and the record. The work itself runs on runners you register, so your code and your AI credentials stay on hardware you control.

A personal runner

Runs only your own work, in the projects you allow it, on your laptop or a spare box. Register one on each machine you have, and they all serve the same projects. Your Claude plan or API key stays on that machine: each job reads it there, and it is scrubbed from everything the job reports.

A project pool

Runs the whole team's work on machines the team shares, with the same setup. Chat and the lead agent can run there too, so a project's conversations use the team's own credentials as well.

Two commands on Linux, a Mac or Windows. The console prints them for you, with a token for the machine.

npm i -g <the runner package the console names>
chuggy-linux register --api https://chuggy.vteng.io --token=… --personal

Jobs run in containers, through Docker or rootless Podman on Linux, Colima on a Mac, and Docker Desktop on Windows. A job can also run on the machine itself, for tools that need it.

Where it is, and where it is going

Today

  • The fourth version of chuggy, built on what three earlier ones taught us.
  • More than 1,100 pull requests merged on this version, many of them written by agents running on chuggy and landed by chuggy.
  • BattleBuffet, a game built with chuggy, is live on Twitch.
  • The first outside team is running work on its own machines.

Next

  • Runners we host, so a team can start with nothing installed.
  • Machines that join from the cloud when the queue is long.
  • Paved paths for the things helpers build, such as accounts, data, payments and domains, so that approving a change can mean it goes live.
  • Windows runners for Unity, and large assets tracked beside the code.

For developers

Your repository names the environment

A project is one or more GitHub repositories. Each holds configurations in .chug/configurations/ that name the image jobs run in, the work stage, the evaluation stages of check commands or reviewing agents, and how a ticket lands: a push, a pull request, or a pull request then a merge. Every key is in the published schema.

A job is a container of your image

It runs as uid 1000 with chuggy's runtime mounted read-only, the repository cloned to /workspace/repository, and 2 CPUs and 4 GiB unless the configuration asks for more. Build caches, Docker inside a job, and jobs on the machine itself are in the docs.

Two GitHub Apps split authority

Chuggy Portal lands finished work and can be the only thing besides admins allowed to update main. Chuggy Worker mints a job's short-lived credential for its branch and nothing more.

Your coding agent gets the same tools

One line gives Claude Code the tools a chuggy session has: read, draft and release tickets under your own sign-in.

claude mcp add chuggy -- chuggy-linux mcp --site https://chuggy.vteng.io --workspace … --project …

The rules are proved before they are coded

chuggy's core is a formal model in Quint. The implementation is checked against traces the model emits, and when the two disagree, the code is wrong.

Everything is public on GitHub

The orchestrator and its cluster can be read by anyone and used only with a license. The runners are MIT, so anyone can install one.
