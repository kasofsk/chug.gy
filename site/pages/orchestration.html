Build confidently with adversarial review.

Chuggy's formal specification and battle testing ensure unattended software development is safe, stable and correct.

  1. 1

    Draft

    Write the brief yourself, or talk it through with an agent that drafts it for you.

  2. 2

    Release

    Release the ticket when the brief is ready. It starts once the tickets it depends on are done and you give the go-ahead.

  3. 3

    Work

    An agent makes the change on a separate branch, in a fresh container.

  4. 4

    Evaluation

    Your checks run, a reviewing agent reads the diff and, where you ask, a person approves. You set the order.

  5. 5

    Landing

    The change merges by push, by pull request or through the built-in merge queue.

A failed check or review sends the work back with the findings. After a set number of cycles, the ticket stops and asks a person.

No agent approves its own work.

The agent that writes a change never approves it. A reviewing agent reads every diff against your written standards. Where you want a person, the ticket waits for one.

  • Staged evaluation

    Evaluation runs in stages. A stage is a command, a reviewing agent or a named approver. A failed stage sends the work back.

  • Sandboxed jobs

    Container jobs start fresh and run as an unprivileged user, with every Linux capability dropped.

  • Credentials stay with you

    Model keys stay on the machine that runs the work. They are mounted read-only, scrubbed from logs and never sent to Chuggy.

  • Hard stops

    Tickets stop at the rework limit. Accounts pause at the usage limit you set.

  • A complete record

    Every prompt, command, diff, review and approval is kept. You can see what an agent did, who signed off and when.

  • A formally specified core

    The core that moves a ticket from stage to stage has a formal specification, and the implementation is tested against it.

Your process is a file in your repository.

A project's rules are plain files in its repository. A change to the process is a pull request, like any other change.

A run shows what filled its context window.

Chuggy records the context of every agent run. Open one to see how full the model's window was, what filled it and how it grew with each call.

  • Window

    How much of the window is in use, split by system prompt, tools, memory files, skills and messages.

  • Growth

  • Inputs

    The brief, instructions, settings, tools and skills the agent was given before its first call.

Features

Orchestration

  • Dependency graphsTickets declare what they wait on, and Chuggy works out the order.
  • EpicsGroup related tickets under one goal and follow one progress bar.
  • Parallel executionIndependent tickets run at the same time, each in its own workspace.
  • Automatic reworkFailed work returns to the agent with the findings, up to a set number of cycles.
  • Stacked landingsEach change is checked on top of the ones queued ahead of it, and the stack merges in order.
  • Conflict handlingWhen the target branch moves, the change is merged with it and checked again. The agent resolves any conflict.

Review and control

  • Staged evaluationChecks, agent review and approval, in any order.
  • Agent code reviewA reviewing agent reads every diff against your written standards.
  • Human approvalRequire a developer, an admin or a named person to sign off before a change merges. An agent cannot give that approval.
  • InboxTickets that need a person arrive in one place, with the reason.
  • Usage limitsSet a percentage of your plan's usage window. The account pauses when it's reached.
  • RevokeStop a ticket at any point before it merges. Its record stays.

Run records

  • Context viewerSee what filled a run's context window and how it grew, call by call.
  • TranscriptsRead a run's transcript, with its tool calls and their results.
  • Cost per runSee how long each run took, the tokens it used and their cost at list price.

Runtime

  • Your imagesJobs run in the container image your project names.
  • Host jobsWork that needs Xcode, a GPU or a device runs directly on a machine that has it.
  • Claude Code and CodexChoose the agent and model for each kind of job.

Team and administration

  • Roles and permissionsDecide who can file tickets, start work, approve and administer in each project.
  • Single sign-onSAML and OIDC with your identity provider.
  • Audit logEvery action and who took it, ready to export.
  • Usage dashboardsEstimated spend, run time and throughput, by project, model and member.
  • Multi-repository projectsOne project can span several repositories.
  • Self-hostingRun all of Chuggy inside your network.

Integrations
