The problem

Compiling is not the bar. Matching the baseline is.

When software sits underneath flood, reservoir and water quality decisions, a change is only finished when someone can show what was asked, what was run and why it was accepted. A chat window per engineer does not produce that.

Nobody can say what the agent was asked

The prompt lived in one person's session and is gone. The next reviewer sees a diff with no brief behind it.

A tidy refactor quietly moves the numbers

The solver still converges and the build is green. Whether results still match depends on whether anyone remembered to run the comparison.

The client asks how it was tested

And the honest answer is a story reconstructed from memory, because each person used the tools their own way.

How a change moves

One path for every change, and a person at both ends.

A ticket's brief names the problem, what to build, what not to touch and how to verify it. Nothing starts until a person dispatches it, and what lands is what passed your plan.

  1. 01
    Draft and release

    Written by you or by an agent on your word. Released tickets wait on the tickets they depend on.

  2. 02
    Dispatch

    A person who may dispatch starts it. Releasing alone starts nothing.

  3. 03
    Work

    An agent makes the change on its own branch, in a container on your runner.

  4. 04
    Evaluation

    Your plan's stages run in order. A stage that fails sends the work back with the reason.

  5. 05
    Landing

    A push, or a pull request left open for a person to merge. Your choice per ticket.

Configurable Escalation Policy

A ticket that fails evaluation too many times, is self-contradictory or insufficiently stated, or whose landing cannot go through, is escalated for human review.

Who it answers to

More throughput, simpler governance, and a record ready for any question.

THE ENGINEER · THROUGHPUT

"Can I hand off more than one thing at a time?"

  • The brief is the instruction: intent, links to read first, the branch, the checks.
  • Tickets become ready in order as the tickets they wait on finish, so a queue of work keeps moving.
  • File and follow tickets from the console, a chat thread, or your own coding agent.
THE TECHNICAL LEAD · GOVERNANCE

"Who decided this was good enough?"

  • The evaluation plan is a file in your repository, reviewed and versioned like the code.
  • A plan can list a person's approval as an evaluator, after the checks and the reviewing agent.
  • Each ticket is pinned to the plan revision it was dispatched on.
THE CLIENT · TRANSPARENCY

"We have a question nobody planned for."

  • chuggy keeps the record of what ran, what it decided and why.
  • Each job has its own log; each failed stage has its reason.
  • The answer is read from the ticket, the same way for every change.
Where it runs

Your machines. Your model accounts.

The agent's work and its evaluation run on runners you register. Which model account a machine uses is set on that machine, so the choice stays with you and your client.

chuggy works with GitHub repositories today. Whether a given model account is approved for a given contract's code and data is a decision for you and your client; chuggy lets you make it per machine.

Runners
Linux, Mac or Windows machines of your own. Each job runs in a container as an unprivileged user with every capability dropped.
Credentials
Read on the runner from a file mounted read-only, scrubbed from what a job reports, and never sent to chuggy.
Model access
A Claude subscription or API key, or Claude through Amazon Bedrock, Google Vertex AI or Microsoft Foundry. A Codex login also works.
Deployment
Hybrid cloud and on-premises deployment are supported.
Open to inspection
The core is a formal model specified in Quint. The service and the three runner packages are public on GitHub.
Start small

One repository, one test suite you already trust.

  1. 1
    Pick the repository where a regression suite already tells you when results move.
  2. 2
    Write the plan down: the image to build in, the checks to run, who reviews, how it lands.
  3. 3
    Register one runner, a machine you already build on.
  4. 4
    File a ticket you would give a new hire: a missing test, a documentation fix, a small port. Land it as a pull request and read the record.
